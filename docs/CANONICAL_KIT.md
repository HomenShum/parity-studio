# Canonical ui_kit zip — the import / export contract

Parity Studio's drop-zip importer and Export-ZIP endpoint share one
shape: the **NodeBench AI Skill-pack format**. This is the same shape
Anthropic Claude Code Skills consume, so a kit you export here is
loadable as a Claude Skill without further conversion.

A canonical zip looks like this:

```
<root>/
├── README.md                    # kit-level brand narrative + usage
├── SKILL.md                     # Claude Skill descriptor (frontmatter)
├── colors_and_type.css          # shared brand tokens (source of truth)
├── assets/                      # SVG logos, webp hero/og, mask icons
├── preview/                     # one HTML specimen per token / component
├── explorations/                # WIP layouts (optional)
├── scraps/                      # working PNGs (optional)
├── screenshots/                 # final composed screenshots (optional)
├── uploads/                     # original source PNGs that fed the kit
└── ui_kits/
    ├── <slug-1>/                # one product per slug
    │   ├── index.html
    │   ├── components/*.tsx     # or *.jsx — drop-in components
    │   ├── tokens.css           # per-kit overrides over colors_and_type.css
    │   ├── manifest.json        # schemaVersion + slug + index path
    │   ├── README.md            # per-kit handoff instructions
    │   └── HANDOFF.md           # generated by parity-studio export
    ├── <slug-2>/
    └── ...
```

## Required vs optional

| Path | Required? | Importer behavior | Exporter behavior |
|---|---|---|---|
| `README.md` (root) | optional on import, **emitted** on export | If present, the SKILL.md description seeds the run prompt | Auto-generated kit-level brand narrative |
| `SKILL.md` | optional on import, **emitted** on export | `description:` field becomes the run prompt for provenance | Auto-generated frontmatter pointing at the active slug |
| `colors_and_type.css` | optional, **emitted** on export | Read but not yet merged into the active run | Stub that imports `ui_kits/<slug>/tokens.css` so consumers have a single root token entry |
| `ui_kits/<slug>/...` | **required on import** | Parsed, the largest slug becomes the active run; other slugs are noted but not run | One slug per run (the latest ui_kit produced) |
| `assets/` | optional | Currently ignored on import | Currently not generated on export (TODO) |
| `preview/` | optional | Currently ignored on import | Currently not generated on export (TODO) |
| `uploads/<*.png\|jpg\|webp>` | optional | First image ≤ 2 MB becomes the run's `sourceImageBase64` for the source-image popover | The original source image is exported back here |
| `explorations/`, `scraps/`, `screenshots/` | optional | Ignored | Not generated (TODO) |

## Multi-slug zips

The canonical NodeBench zip ships **multiple slugs** in `ui_kits/`
(`nodebench-web`, `nodebench-mobile`, `nodebench-workspace`,
`nodebench-mcp`). The importer:

1. Picks the slug with the **most files** as the active run.
2. Notes the remaining slugs in the composer status line — they are
   preserved upstream (in the user's filesystem) but parity-studio
   only carries one slug per run today.
3. Future work: a follow-up could let the user pick which slug to
   activate, or split a multi-slug zip into N runs. Not done yet.

## Why symmetric?

If the way IN matches the way OUT, you can:

- **Round-trip**: export → unzip → re-import without information loss.
- **Library**: keep a folder of canonical zips (NodeBench, your own
  brand, a partner's) and drop them onto parity-studio to start a run
  pre-populated.
- **Skill compose**: an exported zip drops directly into Claude
  Code's `.claude/skills/` directory and becomes a self-describing
  Skill.

## File caps (importer)

To keep a run row sane:

- **Total zip size**: ≤ 30 MB
- **Per-file size inside the kit**: ≤ 200 KB (matches `patchFile`)
- **Source image inside `uploads/`**: ≤ 2 MB (matches `runs.start`)

Files above these caps are silently skipped on import; the user gets
a status line listing what landed.
